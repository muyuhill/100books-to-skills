# 《精益创业》—— 用科学方法创业，而不是赌运气

> 创业不是建一座城堡然后请人来看——是开着一辆能跑的车在迷雾里找路。方向比速度重要，数据比直觉可靠。

埃里克·莱斯的核心主张：**创业是一场科学实验，不是一场赌博。** 你不能靠「我觉得会成功」——你得用最小的代价快速验证假设，然后根据真实数据调整方向。

---

## 一个核心循环：Build → Measure → Learn

```
┌─────────────────────────────────────┐
│                                     │
│   Ideas ──→ BUILD ──→ Product      │
│     ↑                      │       │
│     │                      ↓       │
│   LEARN ←── MEASURE ←── Data       │
│                                     │
└──────── 越快完成一圈，浪费越少 ────┘
```

### 这不是「先想好再做」

传统做法：花半年写商业计划书 → 花一年开发产品 → 上线发现没人要。

精益做法：两周内做出一个粗糙版本 → 扔给真实用户 → 听他们说什么 → 调整 → 再来一圈。

**关键是速度**：每一圈的目的不是为了把产品做完美，而是为了更快地发现「什么值得做」。

### 三个步骤拆解

| 步骤 | 做什么 | 常见错误 |
|------|--------|---------|
| **Build** | 用最少资源做一个能测试假设的东西 | 做太多、做太精、舍不得砍功能 |
| **Measure** | 收集用户真实行为数据（不是问卷） | 看虚荣指标、只看正面数据 |
| **Learn** | 判断：继续还是转向？ | 「我们学到了很多」但没有数据支撑 |

**一句话**：你的任务不是建造东西——你的任务是**尽可能快地走完这个循环，找到可行的商业模式**。

## MVP：最小可行产品

### MVP 不是半成品

> MVP 不是「砍掉一半功能的正式产品」——它是一个实验工具。目的不是卖出去，是学到东西。

| | ❌ 不是 MVP | ✅ 是 MVP |
|---|------------|----------|
| **定义** | 简陋版产品 | 用最少资源验证最关键假设的实验 |
| **目标** | 上线、有用户 | 拿到数据、验证或推翻假设 |
| **标准** | 好不好看、功能全不全 | 能不能让我学到东西 |
| **心态** | 「先把产品做出来」 | 「先看看这个假设对不对」 |

### 四种 MVP 形式

1. **视频 MVP**：做一个产品演示视频，看有没有人点「想要」。Dropbox 就是这么起步的——一个 3 分钟视频，注册量从 5000 飙到 75000。

2. **礼宾式 MVP (Concierge MVP)**：人工手动完成服务，假装有自动化产品。不是用软件做——是你自己动手帮用户做，看看他们到底需要什么。

3. **绿野仙踪 MVP (Wizard of Oz)**：用户以为他们用的是自动化产品，但实际上是你（或团队）在后台手动操作。Zappos 创始人就是去鞋店拍照片放到网上，有人下单了再去店里买来寄——没有库存、没有系统。

4. **单功能 MVP**：只做一个功能。不是做很多功能然后看用户用哪个——是只做一个，看它是不是真的解决了问题。

### MVP 的本质问题

> 不是「我能做出来吗？」而是「我应该做出来吗？」

每做一个 MVP 之前，明确写下来：
- 我们在测试什么假设？
- 什么数据能证明这个假设是对的？
- 什么数据代表我们错了？

## 验证式学习 (Validated Learning)

### 学习了 ≠ 验证了

| 一般「学习」 | 验证式学习 |
|-------------|-----------|
| 「我们了解到用户喜欢这个功能」 | 「A/B 测试显示使用率提升了 27%，p<0.05」 |
| 「市场调研说很多人有兴趣」 | 「落地页 300 人访问，23 人留下了邮箱，5 人付了钱」 |
| 「我们觉得方向是对的」 | 「关键指标在过去 3 周持续上升」 |
| 「会上大家一致认为……」 | 「数据表明……所以结论是……」 |

**验证式学习 = 假设 + 实验 + 数据 + 结论**。缺任何一个环节，都不叫验证式学习。

### 如何做验证式学习

1. **明确假设**：「我们相信，[某类用户] 有 [某个问题]，他们会用 [某种方式] 解决它。」
2. **设计实验**：什么是最小的、能测出这个假设对错的动作？
3. **收集数据**：不是「有没有人点」，而是「多少人点、多少人走、多少人付钱」。
4. **得出结论**：假设成立 → 继续。假设不成立 → 转型。

### 一个经典的失败案例

> 「我们花了六个月做了一个完整的产品，上线了，没人用。但我们学到了很多！」

这不是验证式学习。验证式学习是说：「我们两周内做了一个落地页，发现这个价值主张根本没人点——所以我们在浪费更多时间之前转向了。」

**速度 × 真实性 = 验证式学习的价值**。六个月学到的东西，和两周学到的东西，如果结论一样，前者是巨大的浪费。

## 创新核算 (Innovation Accounting)

### 虚荣指标 vs 可操作指标

| 虚荣指标 | 可操作指标 |
|---------|-----------|
| 总注册用户数 | 每周活跃用户增长率 |
| 页面浏览量 | 转化率 |
| 下载量 | 留存率（第 7 天、第 30 天） |
| 「我们被 XX 媒体报道了」 | 媒体报道带来了多少付费用户 |
| App Store 评分 | 评分跟留存的相关性 |

**虚荣指标的特征**：永远在涨，但什么都说明不了。它们让你感觉良好，但不帮你做决策。

**可操作指标的特征**：能让你做出具体决策。看到数据，你知道下一步该做什么。

### 三步创新核算框架

1. **建立基线**：用 MVP 测量现状。用户从哪里来？多少人留下来？多少人付钱？

2. **调整引擎**：每次改变一个变量（功能、定价、文案、渠道），然后测量变化。不是改十个地方然后看整体有没有变好——改一个，测一个。

3. **转型还是坚持**：调整后，指标是否在向理想方向移动？如果没有，而且是持续没有，那就该转型了。

### 三个增长引擎

莱斯提出了三种可持续增长的引擎，你需要知道你的业务靠的是哪一种：

| 引擎 | 机制 | 关键指标 | 例子 |
|------|------|---------|------|
| **粘性式** | 用户用了就不走 | 留存率、流失率 | SaaS 工具、社交平台 |
| **病毒式** | 用户拉用户 | 病毒系数（每个用户带来多少新用户） | 微信、Dropbox 推荐 |
| **付费式** | 花钱获客，边际利润覆盖成本 | 客户获取成本(CAC) vs 客户生命周期价值(LTV) | 电商、广告驱动业务 |

**不要同时优化三个引擎**——选一个，专注。每个引擎需要的策略完全不同。

## 转型 (Pivot) vs 坚持 (Persevere)

### 这是精益创业最难的决定

> 坚持和固执之间只有一线之隔。那根线叫数据。

大多数创业者在该转型时选择坚持——因为沉没成本、面子、团队士气。但也有些人在该坚持时过早转型——因为太容易被数据波动动摇。

### 怎么判断？

**该转型的信号**（不是情绪，是数据的持续趋势）：

- 不管你怎么优化，核心指标（留存、转化、付费）就是不动
- 增长引擎不转：病毒系数 < 1 且无法提升；获客成本持续高于 LTV
- 用户反馈的规律是：「挺好的」但不用——不是某个功能不行，是需求本身不强烈
- 你发现了一个比原计划更有潜力的方向（数据证实的，不是猜的）

**该坚持的信号**：

- 核心指标在改善，只是还不够快（趋势是对的）
- 有一个细分用户群非常活跃（考虑缩小范围，而不是换方向）
- 你还没把当前引擎调到极致（还有很多可做的实验）

### 十种转型类型

莱斯总结了十种 pivot 方式，做个决策检查清单：

| 转型类型 | 改什么 | 例子 |
|---------|--------|------|
| **放大转型** | 一个功能变成整个产品 | Instagram 从 Burbn（功能太多）变成照片分享 |
| **缩小转型** | 整个产品变成一个功能 | 某个功能被平台吸收 |
| **客户细分转型** | 换目标用户 | 卖给大企业 → 卖给小团队 |
| **客户需求转型** | 解决用户的另一个问题 | 原来做约会 → 后来做社交 |
| **平台转型** | 从应用变成平台，或反之 | |
| **商业架构转型** | 高利润低量 vs 低利润高量 | |
| **价值捕获转型** | 换收费方式 | 付费 → 免费增值；一次性 → 订阅 |
| **增长引擎转型** | 换增长方式 | 病毒 → 付费 |
| **渠道转型** | 换分发渠道 | 直销 → 渠道商 → 自营 |
| **技术转型** | 用不同技术解决同一个问题 | |

**转型不是失败——拒绝转型才是。** 几乎所有成功的创业公司，最终的样子都和最初的想法不一样。

### 转型的时间表

> 给自己一个「转型期限」。比如：如果三个月内 XXX 指标没有达到 YYY，我们就转型。

没有期限的目标只是愿望。有期限的目标才是计划。

## 小批量 (Small Batches)

### 为什么小批量 = 更高效

丰田生产方式的核心理念，在软件和创业中同样适用：

| 大批量 | 小批量 |
|--------|--------|
| 一次做 50 个功能，一起发布 | 一次做 1 个功能，测完就发 |
| 问题在最后集中爆发 | 问题立刻被发现 |
| 返工成本巨大 | 返工成本极低 |
| 浪费大量时间在「可能有用」的东西上 | 只做「已验证有用」的东西 |
| 三个月一次发布会 | 一天可以部署几十次 |

### 在创业中怎么用小批量

1. **开发**：一个功能 → 测试 → 上线，而不是五个功能 → 联调 → 上线
2. **用户测试**：找 5 个人测，修完问题再找 5 个，而不是找 50 个人测一次
3. **营销**：一个渠道 → 一个文案 → 测 → 优化，而不是同时铺十个渠道
4. **A/B 测试**：每次改一个变量，而不是改整个页面

### 小批量背后的数学

> 假设每一个步骤有 10% 的出错概率。
> - 10 个步骤串行的大批量：成功率 = 0.9^10 ≈ **35%**
> - 1 个步骤的小批量：成功率 = **90%**

分批不是拖延——分批是**更快地发现问题**。找到问题越早，修它的成本越低。

## 五个为什么 (Five Whys)

精益创业还有一个附带的实用工具——当出现问题的时候，问五次「为什么」，找到根本原因，而不是停留在表面。

### 怎么用

```
问题：网站宕机了 30 分钟。
1. 为什么？→ 服务器 CPU 跑满了。
2. 为什么 CPU 跑满了？→ 有一个查询没有索引。
3. 为什么没有索引？→ 开发的时候忘了加。
4. 为什么忘了加？→ 我们没有 code review 流程。
5. 为什么没有 code review 流程？→ 团队觉得「太慢了，没必要」。

真正要解决的问题不是「加上索引」——是建立 code review 流程。
```

**原则**：
- 每次「为什么」不要把矛头指向人（「因为张三忘了」→ 没用）
- 要指向流程和系统（「为什么流程允许张三忘记？」→ 有用）
- 按比例投入：第一次发生小问题，做个小修复；反复发生，就修流程

## 一句话总结

> **创业就是在一个极端不确定的环境中，用科学方法找出什么是值得做的。** 所有不产生验证式学习的工作，都是浪费。

当你面对一个创业想法时，不要问「能不能做出来」——要问「我怎么在两周内知道这个想法对不对」。
